## Business outcome

A **platform operator** (Ship Dễ back-office staff) can provision a new merchant shop and its initial owner account without requiring the shop owner to self-register. This enables onboarding scenarios where the operator sets up accounts on behalf of merchants (phone sales, field agents, batch migration), bypassing the public self-service registration flow (`FEAT-AUTH-01`). The provisioned account is immediately `ACTIVE` and ready for login (once `FEAT-AUTH-03` is available), with no email/phone verification step required because the operator vouches for the identity.

## Author boundary

`GEMINI` is required because:

- Authentication guard infrastructure (API key admin auth) is a security/tenancy decision.
- Creates new tenant boundaries (`Merchant`/`User`) from an admin path, requiring authorization judgment.
- Spans backend API, persistence migration, and integration tests — cross-layer vertical feature.
- Failure in account provisioning (partial tenant, duplicate owner) is a data-integrity concern.

Consequential decisions for human confirmation during PR review:

1. Admin authentication: uses a platform-admin API key (`X-Platform-Admin-Key` header) validated against `PLATFORM_ADMIN_KEY` env var. A full RBAC admin user model is out of scope.
2. Admin-created accounts skip all verification (immediately `ACTIVE`) because the operator vouches for identity.

## In scope

- `POST /admin/shops` — Create merchant + initial OWNER in a single transaction.
  - Body: `merchant_name`, `owner_full_name`, `owner_email` (optional), `owner_phone` (optional), `owner_password` (optional, auto-generated if omitted).
  - At least one of `owner_email` or `owner_phone` required.
  - Sets verification timestamps for provided channels (operator-vouched).
  - Returns created shop details and temporary password (if generated).
- `GET /admin/shops` — List all merchants (paginated).
- Admin API key guard (`X-Platform-Admin-Key` vs `PLATFORM_ADMIN_KEY` env var).
- Canonical errors: `VALIDATION_ERROR`, `DUPLICATE`, `FORBIDDEN`.
- Audit log for `ADMIN_CREATE_SHOP`.
- Prisma migration: `created_by`, `activated_at`, `created_by_ip` on `User`.
- Integration tests (Supertest) for all acceptance scenarios.
- OpenAPI spec update.

## Out of scope

- `FEAT-AUTH-01` (self-registration) — already merged, not modified.
- `FEAT-AUTH-03` (login), `FEAT-AUTH-04` (password recovery).
- Full RBAC admin user model with login/sessions.
- Admin UI/operator dashboard — API only.
- Bulk import / CSV batch provisioning.
- Modifying or deactivating existing shops.
- `FEAT-USR-01`/`FEAT-USR-02` (additional user invitations).

## Business rules and edge cases

| Rule ID      | Rule                                                                                                       |
| ------------ | ---------------------------------------------------------------------------------------------------------- |
| BR-ADMIN-01  | Requires valid `X-Platform-Admin-Key`. Missing/invalid returns `403 FORBIDDEN`.                             |
| BR-ADMIN-02  | `merchant_name` required, 2-255 characters.                                                                |
| BR-ADMIN-03  | At least one of `owner_email` or `owner_phone` must be provided.                                           |
| BR-ADMIN-04  | `owner_email` format validated (same regex as FEAT-AUTH-01).                                               |
| BR-ADMIN-05  | `owner_phone` format validated (same VN phone regex as FEAT-AUTH-01).                                      |
| BR-ADMIN-06  | If `owner_email` matches existing ACTIVE user, return `400 VALIDATION_ERROR` with `DUPLICATE`.             |
| BR-ADMIN-07  | If `owner_phone` matches existing ACTIVE user, return `400 VALIDATION_ERROR` with `DUPLICATE`.             |
| BR-ADMIN-08  | If `owner_password` omitted, generate 16-char alphanumeric temporary password and return it.                |
| BR-ADMIN-09  | `owner_password` (if provided) minimum 8 characters.                                                       |
| BR-ADMIN-10  | Created User: `status=active`, `role=OWNER`, verification timestamps set for provided channels.            |
| BR-ADMIN-11  | `Merchant.code` auto-generated (slugified name + 4-digit random suffix).                                   |
| BR-ADMIN-12  | `User.created_by` set to `'platform_admin'`.                                                               |
| BR-ADMIN-13  | `User.activated_at` set to `now()`.                                                                        |
| BR-ADMIN-14  | Transaction atomicity: if User fails, Merchant rolls back.                                                 |
| BR-ADMIN-15  | Duplicate merchant name allowed; only `Merchant.code` must be unique.                                      |
| BR-ADMIN-16  | Password hashed with `scrypt` (same `password.util.ts`).                                                   |
| BR-ADMIN-17  | Audit log: `ADMIN_CREATE_SHOP` with merchant_id, user_id, actor, IP, correlation ID.                       |
| BR-ADMIN-18  | `GET /admin/shops` returns paginated merchants with owner details.                                         |
| BR-ADMIN-19  | Rate limiting does NOT apply to admin provisioning.                                                        |
| BR-ADMIN-20  | Admin-created accounts immediately `ACTIVE`, no verification required.                                     |

## UI states

API-only (no frontend). States as HTTP responses:

| State            | HTTP | Body                                                                    |
| ---------------- | ---- | ----------------------------------------------------------------------- |
| Success          | `201`| `{ data: { merchant, user, temporary_password? } }`                    |
| Validation error | `400`| `{ error: { code: "VALIDATION_ERROR", fields: [...] } }`               |
| Duplicate email  | `400`| `{ error: { code: "VALIDATION_ERROR", fields: [{field:"owner_email",code:"DUPLICATE"}] } }` |
| Duplicate phone  | `400`| `{ error: { code: "VALIDATION_ERROR", fields: [{field:"owner_phone",code:"DUPLICATE"}] } }` |
| Forbidden        | `403`| `{ error: { code: "FORBIDDEN", message: "..." } }`                     |
| Empty list       | `200`| `{ data: [], meta: { total: 0, page: 1, limit: 20 } }`                |

## API, event and data impact

| Method | Path           | Auth                   | Description             |
| ------ | -------------- | ---------------------- | ----------------------- |
| POST   | `/admin/shops` | `X-Platform-Admin-Key` | Create merchant + owner |
| GET    | `/admin/shops` | `X-Platform-Admin-Key` | List all merchants      |

Data model changes:
- `User.created_by` (`VARCHAR(64)`, nullable) — who provisioned the account.
- `User.activated_at` (`TIMESTAMPTZ`, nullable) — when account became active.
- `User.created_by_ip` (`VARCHAR(64)`, nullable) — IP of provisioning request.

Migration: forward-only, three nullable columns on `users`. No backfill. No destructive changes.
Compatibility: new endpoints only; existing endpoints untouched; `FEAT-AUTH-01` unaffected.
