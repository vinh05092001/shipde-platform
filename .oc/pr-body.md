## Implementation

This is the root-cause pass requested in `.oc/task.md` for the repeated fence-indentation findings. The parser at a768263 already implements the goal; this pass re-verifies it and locks it with a regression test instead of another per-variant patch:

- Root cause (READY-04 / AC-READY-05): text inside ANY fenced block is never a source. An opener is recognised as optional `>` prefixes, then any amount of leading whitespace, then a run of 3+ backticks or tildes; a closer is the same character with length ≥ the opener and nothing else on the line, at any indent. CommonMark indented-code is deliberately not modelled: over-excluding is safe, under-excluding was the recurring bug.
- Review findings 2–3 (fixed in a768263, re-verified green here): an unclosed fence ends when its list container ends, and container closure is checked before comment parsing, so a real acceptance table or a commented URL right after the container is parsed for real.
- New regression test `rejects source links inside minimally or deeply indented fenced examples` covers single-space ` ~~~` fences under a list, a fence line directly after a bullet, and a deeply indented backtick fence. At f1796fb the deep-indent variant returned `ok: true` (the fenced URL supplied the source); it is now rejected.
- Delivery order: `docs/product-spec/work-items/TASK-AI-164.md:10` and register row 270 both say `297`; `python docs/product-spec/scripts/validate_docs.py` passes.
