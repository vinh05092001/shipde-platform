## Business outcome

The Hermes adapter on main currently builds an argv that the real Hermes CLI does not actually have (such as the `run` subcommand, `--candidate-key`, `--no-fallback`, and `--max-attempts`). The adapter must only emit valid options per `hermes --help` from Hermes v0.21.4. This ensures that the adapter successfully calls the CLI without failing due to unrecognized commands or flags.

## Implementation details

- Read `logs/night/hermes-help.txt` as evidence of real Hermes v0.21.4 CLI capabilities.
- Ensure the Hermes adapter emits valid options: pinned model via `-m`, provider via `--provider`, cwd via `--in`, prompt via `-z`, resume via `--resume SESSION`, and the usage report via `--usage-file PATH` when the caller supplies a path.
- Keep `candidateKey` and the no-fallback policy logic on the controller/wrapper side (not pushed into argv).
- Ensure Hermes drops the configured fallback chain by passing `--ignore-user-config`. Note residual risk: built-in defaults or environment variable fallbacks (like `HERMES_INFERENCE_MODEL`) are not excludable based on the CLI help evidence, so some internal fallback logic may remain active.
- Spawn Windows npm shim without a shell (no injection).
- Write `task-ai-63.test.js` to assert the adapter emits only known options based on the help text, and test resume/stop correctly.
- Update existing `TASK-AI-50` assertions only where they encoded the fake argv, marking them with "corrected to real Hermes CLI v0.21.4".
- *Finding (2026-09-29 follow-up, branch `fix/task-ai-63-hermes-durable-handle`)*: the durable-handle question is settled against the real binary; evidence in `logs/night/hermes-durable-evidence.txt`. Under `-z`, stdout carries only the final response text on success and on failure — never a session id (the CLI documents "no session_id line"). The durable handle IS emitted: as `session_id` in the `--usage-file` JSON report, present on a successful run (`20260929_063508_c80aeb`) and null on a failed one. `hermes --resume <id> -z …` verifiably continues that exact session — the resumed run's report carried the same `session_id`, and the exported history holds both turns under one id. Verdict: **RESUMABLE via the `--usage-file` channel only**. `sessionIdFrom` now parses exactly that field and nothing else; the earlier `parsed.handle` / `parsed.session` / `parsed.pid` guesses had no evidence and were removed.
- *Remaining integration gap*: `executePlan` and the `cli.js` dispatch path do not yet pass a `usageFile` path or feed the parsed report to `sessionIdFrom` (they only read stdout JSON), so a real Hermes launch through them still fails closed. Wiring the report path through the controller is follow-up work; a failed run's report (`"session_id": null`) must always remain a hard `HARNESS_NO_SESSION_ID`.
